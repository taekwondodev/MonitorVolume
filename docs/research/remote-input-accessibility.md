# Remote input and the Accessibility grant

## Scope and conclusion

This investigation answers issue #42 for the accepted scope: a native iOS companion sends Volume Up, Volume Down, and Mute over the same Wi-Fi; the iPhone does not display volume level or mute state. The map records those limits as settled and calls out the Accessibility dependency as a decision to resolve (https://github.com/taekwondodev/MonitorVolume/issues/41; https://github.com/taekwondodev/MonitorVolume/issues/40#issuecomment-6196886033).

**Recommendation:** Do not make remote commands depend on the Mac's Accessibility grant. The grant is required by the current global media-key event-tap path, not by the DDC transport, CoreAudio default-output lookup, intent reducer, or HUD. Keep local media-key capture gated on the grant; let an independently authenticated remote ingress submit only the three allowed commands to the same command-handling path. Hardware control must still require a current, seeded, uniquely resolved eligible monitor session, and writes must still re-resolve the selected output. If the grant is absent, remote input can work while local hardware-key capture remains unavailable; if no safe target/session exists, remote commands must be rejected or not admitted and never routed to a guessed display.

This does not resolve the map's separate decisions about pairing/authentication, listener architecture, or the Mac-side pairing surface. The map explicitly notes tension between such a surface and the invisible-lifecycle contract (https://github.com/taekwondodev/MonitorVolume/issues/41).

## Facts: present control path

### What is gated by the tap and permission

At launch, the coordinator starts default-output observation and calls `reopen`; `reopen` opens the interceptor first, and only after success starts permission polling and schedules permitted service validation (`Sources/MonitorVolume/Handler/ApplicationCoordinator.swift:54-63,93-106`). `MediaKeyInterceptor.open` requires an active eligibility lifecycle and `hasAccessibility`; only then does it create the event tap (`Sources/MonitorVolume/Handler/MediaKeyInterceptor.swift:77-94`). The trust query is `AXIsProcessTrustedWithOptions(nil)` (`Sources/MonitorVolume/Handler/MediaKeyInterceptor.swift:46-54`). Apple documents that keyboard event taps require root or assistive-device access, and describes the event-tap API and its permission failure behavior (https://developer.apple.com/documentation/coregraphics/cgevent/tapcreate(tap:place:options:eventsofinterest:callback:userinfo:)).

The callback parses media-key events and passes them to `ControlEligibility.route`. That route consumes a key-down only if the tap owner is active, the phase is `.eligible`, and the resolved target supports the command. Otherwise it passes through. A consumed key-up is paired and consumed to match an admitted key-down (`Sources/MonitorVolume/Handler/MediaKeyInterceptor.swift:149-181`; `Sources/MonitorVolumeCore/Domain/ControlEligibility.swift:239-263`). Thus current *local* input admission is specifically tap-owned.

Permission polling calls `validateActive`; it checks the lifecycle and tap owner, verifies Accessibility, and verifies that the event tap remains enabled. A failure suspends the lifecycle (`Sources/MonitorVolume/Handler/ApplicationCoordinator.swift:108-123,125-149`; `Sources/MonitorVolume/Handler/MediaKeyInterceptor.swift:96-121`). The coordinator's output-change and display-change revalidation handlers also require `eligibility.allowsPermissionPolling`; that property is true only for the active lifecycle phases (`Sources/MonitorVolume/Handler/ApplicationCoordinator.swift:186-205`; `Sources/MonitorVolumeCore/Domain/ControlEligibility.swift:49-57,117-121`). This means those event-triggered revalidations do not run while missing permission has suspended the lifecycle.

The service itself is not directly wired to Accessibility APIs or the tap. But coordinator scheduling passes `permitted: true` only after successful tap open, and passes false on suspension, sleep, and termination. Service revalidation stores this bit and begins a read/validation only when it is true and `eligibility.beginValidation` succeeds (`Sources/MonitorVolume/Handler/ApplicationCoordinator.swift:93-106,168-183,248-264`; `Sources/MonitorVolumeCore/Service/IntentControlService.swift:36-50`). The service requires `permitted`, a matching generation, and active eligibility for `isCurrent`; both initial state reads and writes are gated by that condition (`Sources/MonitorVolumeCore/Service/IntentControlService.swift:75-80,100-125,131-173`). Therefore the *current orchestration* makes DDC control conditional on tap lifecycle success, even though the DDC repository does not itself check the tap or Accessibility.

Default-output resolution is independently implemented by `CoreAudioOutputRepository.resolveTarget`: it reads CoreAudio's default output device, properties, requires DisplayPort transport, and resolves the matching monitor through the C transport bridge (`Sources/MonitorVolumeCore/Repository/CoreAudioOutputRepository.swift:9-46,59-79`). But service calls to that resolver occur only inside permitted service validation / current work (`Sources/MonitorVolumeCore/Service/IntentControlService.swift:36-50,100-110,163-173`). CoreAudio output-change observation is registered at launch, without an Accessibility check, but its coordinator callback discards changes unless the control lifecycle allows polling (`Sources/MonitorVolume/Handler/ApplicationCoordinator.swift:54-57,186-199`).

### DDC, CoreAudio, and HUD permission need

The DDC repository delegates reads/writes to `MVDDC*` transport functions and contains no Accessibility or event-tap operation (`Sources/MonitorVolumeCore/Repository/DDCMonitorRepository.swift:3-101`). The transport dynamically resolves `IOAVServiceCreateWithService`, `IOAVServiceReadI2C`, and `IOAVServiceWriteI2C` and performs I2C operations (`Sources/MonitorTransport/MonitorTransport.c:34-52`). No claim is made that Apple's private `IOAVService` entry points have a public access contract: ADR 0001 explicitly calls out their lack of an Apple contract (https://github.com/taekwondodev/MonitorVolume/docs/adr/0001-follow-default-monitor-audio-output.md). The inspected implementation contains no AX trust query or event tap in the DDC path. This is evidence of code-path independence, not a promise that every OS/hardware configuration authorizes private IOKit behavior.

CoreAudio default-output resolution and its property-listener registration use CoreAudio APIs and have no Accessibility query in the implementation (`Sources/MonitorVolumeCore/Repository/CoreAudioOutputRepository.swift:9-46,53-57,59-79,126-151`). The source inspection shows this as CoreAudio property access rather than an Accessibility query; no platform-permission conclusion is based on an unverified API documentation endpoint. The current coordinator's decision to suppress some reads/revalidations is lifecycle coupling, not an observed CoreAudio permission requirement.

The app-owned HUD is a non-activating `NSPanel` populated by a SwiftUI view. `show` consumes desired intent and display name; it performs no trust check and no event-tap operation (`Sources/MonitorVolume/Handler/VolumeOSDPresenter.swift:23-48,81-97`; `Sources/MonitorVolume/Handler/VolumeOSDView.swift:35-70`). No inspected code evidence makes Accessibility a prerequisite for the HUD. The HUD does expose normal accessibility semantics on its view, which is not the same as requiring the process's Accessibility grant (`Sources/MonitorVolume/Handler/VolumeOSDView.swift:68-70`).

### Intent routing and fail-closed behavior

The coordinator's current accepted-input delegate obtains a session, runs `VolumeIntentReducer.accept`, immediately shows intent in the HUD, then submits the resulting request to `IntentControlService` (`Sources/MonitorVolume/Handler/ApplicationCoordinator.swift:272-280`). The reducer is a pure command-to-intent transformation over a `ControlSession` (`Sources/MonitorVolumeCore/Domain/VolumeIntent.swift:1-55`). Service submission rejects stale generation/session/revision requests (`Sources/MonitorVolumeCore/Service/IntentControlService.swift:53-62`); before every write it resolves the active output again and confirms it still matches the session identity (`Sources/MonitorVolumeCore/Service/IntentControlService.swift:131-173`). Initial session seeding likewise resolves, reads hardware, resolves again, and only then publishes the session (`Sources/MonitorVolumeCore/Service/IntentControlService.swift:100-120`).

## Inferences and smallest viable change

1. **The Accessibility grant is an input-source prerequisite, not an inherent remote-control prerequisite.** The platform documentation ties assistive access to the event tap; the DDC, CoreAudio and HUD code paths inspected contain no such trust check. Therefore remote input should not synthesize or depend on a global event tap. Keep the existing tap admission rules untouched for physical keys.
2. **The minimum conceptual change is to separate input admission from tap ownership.** Add a narrow command-ingress method that takes a `MediaKeyCommand` from a trusted remote adapter and forwards it to the same intent acceptance path, instead of calling `ControlEligibility.route` (which necessarily requires `tapOwnerActive`). Introduce no alternate hardware writer and do not bypass the reducer/session/service checks. `MediaKeyCommand` already represents step-up, step-down and toggle-mute (`Sources/MonitorVolumeCore/Domain/MediaKey.swift:1-20`); current key routing has capability checks (`Sources/MonitorVolumeCore/Domain/ControlEligibility.swift:246-248`).
3. **Independent remote command handling requires separating the service's operational lifecycle from the local tap lifecycle.** Today a failed tap open means no permitted service validation and no `.eligible` session, and the service requires active lifecycle state (`Sources/MonitorVolume/Handler/ApplicationCoordinator.swift:93-106`; `Sources/MonitorVolumeCore/Service/IntentControlService.swift:36-50,75-80`). The smallest *behavioral* seam is a non-tap path that can initiate/revalidate service eligibility and seed a target session without opening the tap, while retaining output identity checks and fail-closed session publication. This likely means representing hardware/session readiness separately from tap permission/availability in eligibility; merely adding a network handler that calls `submit` cannot work, since no session is published in the no-grant launch path. Do not let the remote listener mark arbitrary sessions eligible or use stale seeded state.
4. **Fail-closed routing remains a control-service invariant.** Admit only the three fixed commands after remote peer authorization; require a current eligible session with matching generation and command capability; reject/drop when no trusted initial monitor state is available; preserve pre-write output identity revalidation and readback. Mute unsupported remains a pass/reject policy decision to align with ADR 0001's volume-only behavior, rather than an Accessibility exception (`https://github.com/taekwondodev/MonitorVolume/docs/adr/0001-follow-default-monitor-audio-output.md`). The current local tap path passes unsupported key types through (`Sources/MonitorVolumeCore/Domain/ControlEligibility.swift:246-248`).

These are design inferences, not implemented or tested changes. In particular, the exact type/API change depends on remote pairing/authentication decisions that are still open in issue #41 (https://github.com/taekwondodev/MonitorVolume/issues/41).

## Accepted decisions that constrain the choice

- **ADR 0003** accepts that the tap needs Accessibility and that tap failures/revocation suspend the media-key path, discard pending work, and do not replay it; active lifecycle polls permission, with recovery behavior tied to tap lifecycle (https://github.com/taekwondodev/MonitorVolume/docs/adr/0003-media-key-tap-lifecycle.md). It does not state that every other control source must require the grant. Applying its tap failure policy to remote input would be an expansion of scope, not a direct requirement.
- **ADR 0001** requires exactly one default-output framebuffer, fail-closed ambiguity/missing-target handling, generation-bound target sessions, and output re-resolution immediately before every write (https://github.com/taekwondodev/MonitorVolume/docs/adr/0001-follow-default-monitor-audio-output.md). Remote ingress must preserve these constraints.
- **ADR 0002** assigns feedback to the app-owned HUD and says it represents ordered intent (https://github.com/taekwondodev/MonitorVolume/docs/adr/0002-replace-native-volume-osd-on-macos-tahoe.md). Existing coordinator shows the HUD as part of accepted command handling (`Sources/MonitorVolume/Handler/ApplicationCoordinator.swift:272-280`). This supports using the existing macOS HUD for remote commands; the scope specifically forbids displaying state on iPhone.
- **Issue #41 Notes** also preserve the invisible single accessory process/no-helper topology (#20), no persistent UI except HUD and native Accessibility requests (#19), and unready input passing through to macOS (#21): https://github.com/taekwondodev/MonitorVolume/issues/41. The #19/#20/#21 decisions are summarized in issue #15: one accessory process without helper; no onboarding or persistent interface; silent failures discard pending intent; unready local input passes through; hardware recovery is read-only and backoff-driven (https://github.com/taekwondodev/MonitorVolume/issues/15). A same-network authenticated remote listener is a new input ingress, not necessarily a topology change, but its always-on cost, listener lifecycle and pairing surface remain unexamined. The pairing surface has an explicit contract tension in #41 Notes.

## Consequences of recommendation

Remote commands remain usable when the Mac has not been granted Accessibility, while local media keys continue to pass through / remain unavailable according to the existing lifecycle. The app can still show its macOS HUD for accepted remote intent, without sending levels or mute state back to iPhone. The change increases the importance of separating tap state from hardware readiness: otherwise the current eligibility/service coupling blocks remote control even though the underlying operations do not need the grant. Authentication and same-Wi-Fi membership must not be treated as equivalent without an accepted security design; those open decisions are outside this research question.

## Limits

No remote ingress exists yet, so the proposed seam is reasoned from current call paths rather than exercised. No target-Mac runtime test was run to establish empirical Accessibility-independent `IOAVService` access. The private API has no Apple contract (ADR 0001). The cited Apple CoreAudio documentation endpoint was not fetched in this investigation; the primary evidence for code-path independence is the inspected implementation, not a claim about OS authorization policy. The local source inspection commands were `nl -ba Sources/MonitorVolume/Handler/ApplicationCoordinator.swift`, `nl -ba Sources/MonitorVolume/Handler/MediaKeyInterceptor.swift`, `nl -ba Sources/MonitorVolumeCore/Domain/ControlEligibility.swift`, `nl -ba Sources/MonitorVolumeCore/Service/IntentControlService.swift`, `nl -ba Sources/MonitorVolumeCore/Repository/DDCMonitorRepository.swift`, `nl -ba Sources/MonitorVolumeCore/Repository/CoreAudioOutputRepository.swift`, and `nl -ba Sources/MonitorTransport/MonitorTransport.c`; their output is cited inline by file and line range. The initial repository observation was `git status --short --branch` with output `## HEAD (no branch)`, followed by `fa70e5d fix(build): add ad hoc signing fallback` from `git log -1 --oneline`. No product code or GitHub state was changed.

## Coordinator verification

- Confirmed against the source: `MediaKeyInterceptor.open` suspends with `missingPermission` before creating the tap when `AXIsProcessTrustedWithOptions` is false (Sources/MonitorVolume/Handler/MediaKeyInterceptor.swift:46-94); `ControlEligibility.route` admits a key down only when `tapOwnerActive` and the phase is `eligible` (Sources/MonitorVolumeCore/Domain/ControlEligibility.swift:239-263); `IntentControlService.revalidate` and `submit` require `permitted` and an active lifecycle phase (Sources/MonitorVolumeCore/Service/IntentControlService.swift:36-80); a tap suspension schedules validation with `permitted: false` (Sources/MonitorVolume/Handler/ApplicationCoordinator.swift:248-262). `grep -rn "AXIsProcess\|Accessib" Sources/MonitorVolumeCore Sources/MonitorTransport` returns nothing.
- Added consequence: without the grant, the coordinator also starts the guided Accessibility session (ApplicationCoordinator.swift:256-258). A remote-only user without the grant would be prompted unless that flow is also decoupled from remote readiness.
- Still a hypothesis: that DDC over private `IOAVService` works without Accessibility at runtime. Earlier target-Mac probing in issue #24 established that Accessibility alone suffices, not that DDC needs it. Verify on the target Mac with the grant revoked during implementation.
